## 0. Framing (read first)

- Hermes is a full single-agent runtime (own agent loop, own LLM client, memory, skills, gateway, TUI/desktop/dashboard) that also ships a multi-profile Kanban dispatcher. Hermes Kanban workers are Hermes processes (`hermes -p <assignee> chat -q ...`, `hermes_cli/kanban_db_dispatch.py:2831`).
- ACS is not an agent. It is a coordination bus (SQLite mail + tasks + review gates) under other vendors' CLIs (Claude Code, Codex, Gemini, ...). Hermes is itself one of ACS's harness adapters (`src/adapters.ts:509`).
- So the two overlap only on "task board + dispatcher + review". Most other rows compare a product against a layer it deliberately does not have. "HERMES AHEAD" in those rows is a scope statement, not a quality statement.
- Hermes's own docs say non-Hermes CLI lanes (Codex/Claude Code/OpenCode) are "not yet a paved path" (`website/docs/user-guide/features/kanban-worker-lanes.md:119-125`). That is the one structural gap ACS fills.

## 2. Hermes default review behaviour (verified)

1. Default review assignee = the implementing profile. FACT: `request_review(..., reviewer=None)` does not touch `tasks.assignee` (`kanban_db.py:3435-3440`); `_dispatch_lane_task(conn, row, row["assignee"], ..., lane="review")` spawns that assignee (`kanban_db_dispatch.py:2421-2427`) and force-loads `sdlc-review` (`:2119-2122`). The docs say it in one line: "spawn the assigned profile with the bundled sdlc-review skill" (`kanban.md:325`).
2. It is a new process and a new run, with prior history visible through `kanban_show`. FACT (`claim_review_task`, `kanban_db.py:2304-2312`). Whether the model/context differs depends only on whether the profile config differs between lanes (it does not, by default).
3. Cross-family rule: none. Verdict-weighted routing: none. Single reviewer verdict closes the transition (`kanban_complete` or `kanban_request_changes`). FACT (negative, grep-based; see 4a).
4. Overrides that exist: `reviewer=` on handoff (must be an installed profile, `tools/kanban_tools.py:833-840`), operator `assign`, `review_dispatch: false` for human review, `kanban create --assignee <reviewer>` then `request-review` (`kanban_db.py:3420-3426` comment), per-task `--model`. Re-review auto-targets the prior reviewer (`kanban_db.py:3483-3496`), which *reinforces* reviewer continuity rather than diversity.
5. Round diversity is addressed by prompting (lenses by round, `SKILL.md`), not by model or family diversity.
6. Evidence-based gate exists for PR work: GitHub required checks must pass at completion, read as the assignee's `gh` identity (`kanban.md:48-95`). This is the strongest non-LLM review gate in either product.

## 3. Where Hermes is ahead (be honest)

- It is a finished agent runtime, not a bus: memory, skills, curator, cron, 25+ messaging platforms, TUI, desktop, dashboard, local-model manager. ACS has none of these by design.
- Kanban depth: attempt-level `task_runs`, exit-code taxonomy (75/78), terminal-provider breaker, protocol-violation budget, respawn guards, PID+fingerprint crash recovery, goal-mode judge, decomposer, board-per-project, tenant namespace, idempotent create, scheduled start, bulk ops, dashboard board with drag-drop (rows 1, 2, 7, 12).
- Workspace lifecycle owned by the dispatcher (scratch/dir/worktree, artifact preservation), vs ACS leaving worktrees to the operator (row 3).
- Evidence-bound completion for PRs (required checks, SHA-bound, per-profile `gh` creds). ACS reviewer is a trusting agent or human; submissions carry self-reported `validation` (`FULL-GUIDE.md:252`).
- Provider and auth breadth, credential pools, fallback chains, OAuth subscription logins (row 11).
- Automated reviewer dispatch: a card in `review` gets a worker spawned; in ACS a reviewer must itself be woken and run correctly.
- Maturity signals (INFER, not measured): very large docs and test tree, many numbered issue references in docs (`kanban.md:95`), versus ACS's 2.9k-line `src/` core and tests dir. This is size and age, not correctness.

## 4. Where ACS could earn an edge (hypotheses, not claims)

H1. Cross-family review as a *shipped, enforced* default. Hermes defaults to same-profile review and has no family rule. ACS already has the policy code (`router.ts:262-266`) but it is unwired. Wiring it into `task review` (reject accept/revise from an agent whose `model.family` equals the assignee's, or auto-assign the reviewer) would be a real differentiator IF evidence shows same-family review misses more defects. No data in either repo supports that yet; treat as untested.
H2. Heterogeneous fleet on one bus. Hermes says non-Hermes CLI lanes are not paved (`kanban-worker-lanes.md:119-125`). ACS's adapters (Claude Code, Codex, Gemini, Kimi, OpenCode, Cursor, Grok, Hermes) already work today by README. Hypothesis: users who already pay for several CLIs prefer a bus to a new runtime. Marketing-level, needs user evidence.
H3. Complementary rather than competing: ACS can already run Hermes as a worker (`adapters.ts:509-529`). A bus that coordinates Hermes profiles plus other CLIs with cross-family review is an integration story, not a rivalry. The gap in that adapter: it uses `--yolo` and scrapes ANSI output and a token count by regex (`adapters.ts:514,520-529`), so it is fragile to Hermes output changes (INFER).
H4. Collision *prevention* via path-scope leases, versus Hermes's after-the-fact reconcile-by-third-profile convention. Hypothesis: fewer merge conflicts in parallel campaigns. Needs an A/B. Caveat: leases are unenforced and need accurate `--scope` declarations (`security.md:28`).
H5. Footprint and cold start. ~129 KB npm tarball, ~4-5 MB Rust binary, no daemon, no Python. Plausible edge for constrained machines and CI; unmeasured against Hermes's install here.
H6. Agent-identity attribution: verified `from`, per-agent tokens, no tool accepts a spoofed sender (`security.md:11`). Hermes's profiles are "one uid, full trust" (`kanban.md:137`). Edge for audit-minded teams; limited by the same-uid caveat both share.
H7. Exportable cross-actor trace (`qagent trace --format html`) including inter-agent mail. Plausible niche advantage; Hermes's `task_runs` and events are richer per attempt, so the claim should be limited to "messages and tasks in one timeline".
H8. Close the closeable gaps first, because several ACS advantages are "design present, enforcement absent": enforce `optionalApiCostBudgetUSD` (config.ts:152-153), write the `usage` table, ship stalled/trace/roster in a tagged release (all are [Unreleased]), and port `supervise --roster` to Rust (not found in `origin/rust-port:rust/src/cli.rs`).

## 5. TS main vs Rust rust-port (ACS only)

- Shared: SQLite schema, token files, signal files, event semantics; interop tested live per `rust/README.md`.
